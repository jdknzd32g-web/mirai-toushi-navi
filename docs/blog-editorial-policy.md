# 日次ブログの編集・図解基準（2026-10-01確定）

2026年10月2日付の新規原稿から適用する。既存の毎朝7時（Asia/Tokyo）の2記事制作・検査・Drive同期・公開フローで必ず読む。日付だけ変えた前日原稿や、同じ図に違う見出しを付けた記事を作らない。

## 本文：読者が理解し、動ける文章にする

- 最初に `editorial/ryo-voice-guide.md` を読む。問いかけ、読者への共感、例えの仕組み、数字や画面の具体例、今日できる行動をつなぐ。毎回同じ導入・口癖・締めをコピーしない。
- 例え話を最低1か所入れる。単に「レシートのようなもの」と置かず、何と何が対応するか説明する。制度の条件や例えで説明できない部分も本文に残す。
- 太字の強調は本文・まとめの要点へ配置する。導入は問いかけと短い段落で読みやすくし、共通CSSを変えて強調の検査を回避しない。
- 計算例または具体的な画面・書類の確認例を最低1つ入れる。数値例には仮定・計算・対象期間を明記し、実際の利率・税額・本人の実績と混同させない。操作例には入口、読む項目、完了確認を入れる。確認できない導線は作らない。
- 読者が最後に何を出し、何を転記し、どこへ確認するかを示す。注意書きや同じ結論で段落・FAQを埋めない。
- 公式の一次資料で条件と日付を確認する。過去台本は話し方の参考であり、制度・税率・現在の投資判断の根拠にしない。

## 小見出し図解：見せたい関係から構図を選ぶ

重要なH2の直後に2〜4点。全見出しへの機械的挿入は不要。同じ記事では最低2種類を使う。紺・黄の共通配色と16px以上の文字を維持し、構図と情報の関係を変える。

| layout | relation | 向く説明 | 追加データ |
| --- | --- | --- | --- |
| allocation | partition | お金などを用途別に分ける | `origin`、2組のcards |
| timeline | time | ある境目の前後、待機期間 | 3つの`axis`、2つの`periods`、2組のcards |
| document | location | 書類のどの欄を見るか | 2行の`document_heading`、2〜6組のcards |
| decision | condition | 条件を確認して判断が分かれる | 2〜4組のcards、2組の`outcomes` |
| flow | sequence | 操作・作業の順番 | 2〜3組のcards |
| record | record | 照合・転記メモ | 2〜3組のcards |

各図に `title`、`layout`、`relation`、`reason`、`cards: [[見出し, 説明]]` を保存する。`reason` は「時間の前後を区別するため」など、本文のどの関係を見せるかを書く。allocation/timeline/document/decisionには `note` も必須。書類の模式図には実際の書式ではないこと、判断図には省けない条件と分岐後の注意を書く。時間軸の日付・期間、書類名、判断結果は記事データに指定する。国債や年金の文言は共通部品に固定されていない。

直近7記事の図解を確認する。同じ日の2記事で同じ構図の組み合わせを使う場合、または同じ組み合わせが直近7記事中3記事以上に現れる場合は、内容上その関係が必要な理由を `editorial_quality.diagram_repeat_reason` に20文字以上で記録する。見た目を変えるために因果・条件・時系列を誤って表さない。色や箱のラベル変更だけを構図変更と扱わない。

`cards`の省略時レイアウトは旧原稿互換専用。10月2日以降は使わない。自由なHTML/CSS、未確認の制度条件、架空の書類欄を入力しない。

## ヘッダー写真：直近7記事と比較する

人物構成・視点・主要小物・背景を確認する。夫婦と机、手元と書類、抽象的な箱を毎回の標準にしない。記事固有の行動や仕組みから写真の構図を作り、同日の2記事も異なる場面にする。画像生成プロンプトと比較理由は既存の `editorial/image-prompts/` に残す。年代語を生成プロンプトへ入れないという既存ルールも維持する。

比較する記事IDは次で取得する。未来日付や同日の相方は直近7記事に含めず、相方との比較は別に行う。

```sh
python3 tools/blog_pipeline/editorial_policy.py --date YYYY-MM-DD
```

## 原稿に残す検査データ

`design.policy_version` を `2` にする。`editorial_quality` に以下を残す。quote/actionは見出しや編集メモではなく、本文に実在する一節をそのまま記録する。

- `voice_reference`: `editorial/ryo-voice-guide.md`
- `analogy`: `quote`（例えの説明）、`limit`（その例えが説明できない条件）
- `example`: `quote`（具体例）、`kind`（calculationまたはwalkthrough）、計算なら `assumptions`。操作・書類の確認例なら `completion_quote`（完了画面や最終照合項目を確かめる、本文に実在する一節）も記録する。入口や入力内容だけで終わる操作例は合格させない
- `action`: 読者に示した具体的な次の行動
- `hero_review`: `recent_article_ids`（取得した7記事IDを順に）、`traits`（viewpoint/people/objects/setting）、`selection_reason`
- `diagram_review`: 同じ7記事IDの `recent_article_ids`、構図を選んだ `selection_reason`
- 同じ組み合わせを必要上繰り返す場合だけ `diagram_repeat_reason`

## 公開ゲート

`pipeline.py build` が上記の入力、本文との対応、図解の関係と種類、直近7記事の照合、同日の写真構図を検査する。不足や定型の無説明な反復は停止する。検査データだけ作って本文に例え・具体例・行動を入れない原稿も停止する。

以降は従来どおり、単体テスト、4画面幅の表示・デザイン検査、Drive同期、quality.py、draft検査、本番検査を順に実施する。`diagram-v2.css` は使う新記事の公開パッケージに含め、すでに同じ版が本番にあれば再利用する。既存の記事・CSSを無断で書き換えない。

機械検査が確認するのは構造と記録の整合。例えが面白いか、話し方が自然か、図の関係が正しいか、一次資料の解釈が適切かは、公開前に文章と図を実際に読んで判断する。検査に合わせて本文を不自然にしたり基準を緩めたりしない。
