# 毎日の自動公開（2026-09-13承認）

## 実行スケジュール（2026-09-13変更）

- `automation-3`「毎日のフォローアップ・ブログ2記事公開」に統合。毎日7時（Asia/Tokyo）、ローカルの本プロジェクトで独立した新しい作業チャットとして実行する。
- 従来のメール・カレンダーフォローアップは平日のみ維持。ブログは土日も実施し、日曜日の休息案内も維持する。
- 旧15分間隔の `sbi-nisa-1` は停止（PAUSED）。昼・夕方の追加実行や15分監視は作成しない。
- 会話履歴ではなく記事台帳・公開記録・X送信記録・editorial-logから未完工程を引き継ぐ。過去日の案件は元の日付を保ち、まとめて不足記事を生成しない。競合や結果不明の送信は停止して報告する。
- メール・予定は確認と報告のみ。記事や公開データへ転用しない。WAIZU・YouTubeの制作や公開は対象外。

日次処理は日本時間7時以降に1回。SBI記事1件・非SBI記事1件を作成し、Drive同期・内容検査・デザイン検査がすべて成功したら、追加承認なしでブログ公開、本番検査、非SBI記事のX投稿まで進める。失敗時は停止して報告する。9月13日は4記事とも公開済みなので追加作成・再公開しない。

## 2026-10-01追加：翌日以降の品質基準

2026-10-02付の新規記事から、制作の最初に `docs/blog-editorial-policy.md` と `editorial/ryo-voice-guide.md` を必ず読む。例えの仕組み、計算または操作・書類の具体例、読者の次の行動を本文に入れ、りょうの語り口を自然に使う。小見出し図解は関係に合った最低2種類を選び、直近7記事と構図・写真を比較する。原稿の `design.policy_version=2` と `editorial_quality` の記録が欠ける場合、ビルドの新しい編集ゲートが公開前に停止する。

毎朝7時の既存 automation-3 は最初に本手順とREADMEを読むため、この改訂を翌日以降も引き継ぐ。新しいスケジュール・追加実行は作らない。10月1日の改訂記事は本番公開済み。翌日の実行で再生成・再公開・再投稿しない。既存の定期実行プロンプトにある固定HTML/CSSとは部品の保護を意味し、各記事の図解を同じ箱に固定する指示ではない。

## 公開手順

各コマンドに同じ`RELEASE_DATE=YYYY-MM-DD`（対象原稿の日付）を付ける。出力は`dist/blog-release-YYYY-MM-DD`。以下は必ず順に実施する。

1. READMEの原稿作成・一次情報確認・重複チェック・Drive同期・単体テスト・デザイン・表示検査を完了し、`quality.py`が合格すること。記事ごとに `editorial/keyword-checklists/YYYY-MM-DD-記事ID.md` のSEOキーワードチェック表を作成し、主キーワードの一覧位置、検索意図、完全重複、意味重複、直近テーマ配分、タイトル・導入・本文・URL、一次資料、誇大表現の各判定を結果報告に必ず添付する。重複チェックでは、記事JSONの`duplicate_review`で既存記事との差分を明記し、さらに`pipeline.py build`のタイトル類似・本文類似ゲートを必ず通す。類似判定で停止した場合は、同じテーマを言い換えて公開せず、別テーマへ差し替える。非SBI記事は直近14日分の主題カテゴリを集計し、年金・退職関連を連日選ばない。新NISA、資産形成、投資信託、家計改善、ライフプラン、税・社会保険、退職金、相続を循環させ、直近7日で同じ大分類は原則1回までとする。一次資料の更新など合理的な例外がある場合は理由を記録する。ヘッダー画像の生成プロンプトには「50代」「60代」などの年代語を入れない。対象読者は記事本文とSEOで表し、画像は記事固有の行動・仕組み・比喩から構図を作る。直近7本のヘッダーと人物構成、視点、主要小物、背景が重ならないか確認し、`editorial/image-prompts/YYYY-MM-DD-記事ID.md` に実際のプロンプトと重複確認を保存する。「夫婦＋机＋家計表」を標準構図にしない。Drive同期は、各管理フォルダ配下の`YYYY-MM-DD`日付フォルダへ保存する。既存ファイル更新を基本とし、更新が安全レビュー・競合・所有者確認で止まる場合は、りょうさん個人運用の正本管理として新規連番ファイルへ同期し、読み戻し確認済みIDをdrive-mapの最新版として扱う。
2. `node tools/blog_pipeline/release.cjs inspect`：現在の本番を取得。ローカル公開ソースは過去のパッケージも含め、本番SHA1が一致したものだけ使用。
3. `python3 tools/blog_pipeline/package_release.py`：当日2記事のみ梱包。SBI/非SBI各1件を要求。既存記事の上書き禁止。共通CSSは同一なら再利用、変更されていれば停止。LPは既存枠の最新3件だけ差し替える。
4. `node tools/blog_pipeline/release.cjs draft`：既存本番マニフェストに対象ファイルだけ追加する。保存済みdeploy.jsonがあれば再作成せず状態を確認。
5. `node tools/blog_pipeline/release.cjs status`：readyを待つ。エラー・不明状態では公開しない。
6. `node tools/blog_pipeline/verify_release.cjs`：本番前の表示・リンク検査。追加で`PREVIEW_URL=<draft URL> node tools/blog_pipeline/design-check.cjs`を実行し、共通デザインも合格させる。
7. `node tools/blog_pipeline/release.cjs publish`：本番の直前状態が変わっていない場合だけ公開。公開ID照合後、published-releases.jsonを記録。
8. `node tools/blog_pipeline/verify_release.cjs --production`：本番を検査。合格後に非SBI記事のX投稿が自動実行される。失敗は公開失敗と投稿失敗を区別して報告する。
9. 既存リモートファイルが保持され、パッケージ外のハッシュ変更がないことを確認。Drive台帳へ公開URLと公開状態を同期・読み戻し、公開・X結果をeditorial-log.mdに記録。

## Drive正本の取得経路（2026-10-06復旧）

Drive資料の取得は接続済みGoogle Driveコネクタを優先する。get_profileで指定アカウント、get_file_metadataでID・MIME・更新時刻・所有者を確認し、その正規URLをfetchする。生ファイルはdownload_raw_file=true・include_base64=falseで取得し、返ったfile_uriのfile_idをdownload_fileへ渡してバイト一致を確認する。返値は文字列URLとは限らないため、署名付きURLや認証情報を表示しない。

取得URLのエラーだけを理由に、別アカウントやブラウザアプリの列挙へ切り替えない。正規コネクタが利用できる間は画面操作を使わず、再読込で競合・認証・取得可否を切り分ける。コネクタが必須接続や承認で止まる場合は、具体的な不足と未完工程を報告する。10月6日朝の実行は記事制作前のcua.getApp応答待ちから中断した。低層の遅延原因は未確定で、この経路変更は画面待ちの回避策。無人実行の完走確認とは区別する。

## ビルド時の既存公開記録の保全（2026-10-06確認）

現行buildと単体検査は、台帳とMarkdown閲覧版を確認待ち表記で再生成する。実行前に記事台帳・公開記録・対応する閲覧版を保存し、検査と最終buildの後、当日2記事以外の台帳行を公開状態・公開IDなども含めて同一内容で戻す。公開済み閲覧版が変更された場合はDriveの現行正本と照合して復元する。翌日のビルドで既存記事をdraftへ戻したり、過去原稿を再公開・再投稿したりしない。

検証レポートをDriveへ同期するときは日付別の正本を維持する。drive-mapがdist/blog-previewの更新されるレポートを指している場合、次のbuild前にその前日の確認済みバイトをeditorial/verification-archive/YYYY-MM-DDへ保存し、同じクラウドID・SHA256を維持してローカル参照だけを移す。当日結果は当日のIDへ同期する。昨日のレポートへ今日の結果を上書きしない。今回の135件の台帳行、前日2原稿の閲覧版と前日3レポートは、この方法で内容を保持している。

## 中断・再開

作成済み記事、パッケージ、deploy.json、published記録、X送信記録を先に読み、未完の工程のみ再開する。本番が自分のdeploy.idなら再公開せず本番検証へ進む。第三者の本番更新があれば停止し、新しい本番からの再梱包が必要。同一エラーの自動反復、確認なしの再送をしない。

認証情報を公開パッケージへ含めない。Git push・フォルダ移動・YouTube側の改変・デザイン基準の緩和・新規有料サービス追加は日次処理に含めない。本番とGitチェックアウトの未同期は継続しているので、リポジトリ丸ごとデプロイは禁止。

## 2026-10-20：Git同期とAPI公開の分離

本番の正本は現在のNetlify公開manifestと確認済み公開パッケージとする。Gitはソース履歴の保存先であり、Gitのpushで本番を更新しない。Netlifyサイト `2674e228-ed72-43a3-be06-05e8441e0823` の `build_settings.stop_builds=true` を維持する。これはGit・build hook・APIのbuild実行を停止する設定であり、既存のファイルmanifestを用いたAPI deployとrestoreは継続できる。deployの自動公開停止や公開ロックへ置き換えない。リポジトリ再接続でビルドが有効になるため、再接続時も停止状態を確認する。

既存automation-3は引き続き本手順を読み、当日分のinspect・梱包・draft・検査・publish・本番検査・X投稿・Drive読み戻しを実行する。時刻・頻度・対象を変更せず、Git同期のための日次再実行や追加公開はしない。Gitにない公開記事・CSS・月別一覧があるため、チェックアウト全体を公開しない。

Git同期を依頼された場合は、作業中の変更と日次実行を確認し、隔離worktreeで両方の履歴を残す通常mergeを準備する。force push・履歴のrebase・autostash・一括addを使わない。source-lockに影響する追加・変更・削除は現在の本番SHA1と個別に照合し、承認されたパスだけ更新する。他の保護ソースとdesign-lockは保持し、pipeline.py verifyを通す。mainへの反映前に同時変更を再確認する。push前後にstop_builds=true、現在の本番IDと全公開ファイルのハッシュが不変であることを確認する。

旧tools/auto-push/autopush.sh（auto_push.shはその別名）とscripts/generate-sitemap.tsは停止用の入口として残す。前者の自動rebase・一括commit/push、後者の2025年限定・旧ドメインsitemap生成は実行しない。sitemapはpublication_sitemap.pyを使う通常の検証済み公開パッケージ工程で更新する。netlify.tomlもGitビルドをskipし、再有効化されても検証を経ないroot公開を失敗させる。
