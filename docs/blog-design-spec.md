## 3. 共通ページ構成案

標準順序：写真ヘッダー → カテゴリ・H1・日付／著者 → 導入文 → YouTubeバナー → 目次 → 本文（H2・図解・説明）→ 必要に応じFAQ → まとめ → 公式LINE → 著者紹介 → 出典・免責・一覧への戻り導線。

広告記事は冒頭で広告表示を行う。関連リンクや口座開設ボタンは専用の任意部品とし、公式LINEの部品や文言と混同しない。出典は必要な本文箇所からも参照できるようにする。

### ヘッダーと図解は別部品

- ヘッダー：記事内容に合う写真調の16:9画像。タイトルの前に配置。角丸10px。画像に長文タイトルを焼き込まない。既存素材の権利・用途を確認し、代替テキストと寸法を設定する。
- 本文図解：重要なH2の直後。紺を基調に、白文字・黄色アクセントで比較や手順を説明する。全見出しに機械的に挿入せず、理解に役立つ箇所を選ぶ。
- デスクトップの図解は既存の720×405相当の比率を基準にする。ただしスマホでは縦積み・簡略化・HTML文字への分離を許可する。単純縮小で小さい文字を作らない。
- 図解の要点は本文でも読めるようにする。SVGの場合は説明可能なアクセシブル名を付ける。

## 7. ローカル／マイドライブの役割

| ローカルで正本管理 | マイドライブで管理する編集情報 |
| --- | --- |
| HTMLテンプレート、共通CSS、リンク設定、画像・図解部品、生成処理、テスト、デザイン仕様・承認済み基準 | 記事台帳、原稿、調査メモ、重複確認、りょうの文体・編集方針、確認結果・設計書の共有コピー |

Driveは編集情報の蓄積・共有に使う。Driveへ保存するだけでは表示崩れは防げない。表示の維持はローカルの共通部品と自動検査で行う。仕様の共有コピーには版・更新日を付け、ローカル正本との食い違いを防ぐ。今回はDriveへの追加・更新は行わない。

本文生成はタイトル、要約、節、図解データ、出典などの内容のみを更新する。記事ごとの自由なCSS、公式リンク変更、LP全体の編集を生成処理に任せない。

LPは承認された最新記事枠のみを更新し、表示件数は現行試作の上限3件を維持する案とする。全記事は一覧・カテゴリへ収め、記事追加ごとにホームの表示件数を増やさない。LP全体の再デザインは今回の対象外。

## 8. 実装と確認の順序（次工程）

1. 主基準の記事とLINE・YouTubeの固定文言を確定する。
2. 共通部品・デザイントークンを生成テンプレートに実装する。承認前に現行デザインロックを差し替えない。
3. 試作2記事に適用し、必要な本文図解を作成する。
4. 1440／768／390／320pxで画像・図解・表・長い見出し・導線を確認する。
5. 目次・内部リンク・画像・一覧・カテゴリ・サイトマップの整合、LPの保護領域と最新記事上限を検査する。
6. ローカルでユーザーが確認し、承認された表示を新しい比較基準・デザインロックにする。
7. 検査不合格なら自動公開を止め、修正対象を報告する。公開は別途指示があるまで行わない。

完成条件は「共通部品の存在と配置」「色・余白・幅の統一」「スマホで図解が読める」「公式リンクの一致」「LPの保護」「ユーザーのローカル確認」。記事ごとに写真・文章・図解内容が異なるため、記事全体の画像一致を要求せず、固定部品とレイアウトを比較する。

## 10. 承認後の実装・検査仕様

`tools/blog_pipeline/design-check.cjs`を追加。基準HTMLは`editorial/source-lock.json`のハッシュで固定し、検査の都合で自動更新しない。生成記事全件を1440・768・390・320pxで検査する。

- 実際の計算済みCSSを参照記事と比較：本文色・フォント・行間、最大幅、ヘッダー比率・角丸、H1/H2、カテゴリ、導入・目次、YouTube、LINE、まとめ、著者写真。
- 必須部品の表示とDOM順序・画面上の順序、公式URL・安全な外部リンク属性、画像、目次アンカー、本文16px以上、横はみ出しを検査。
- 図解は見出しの直後、説明可能な名前、複数カードを必須とし、スマホの縦積み・文字サイズ・はみ出しを検査。
- ブラウザー内で故障注入9件を実行し、部品欠落・公式URL改変・配色変更・幅変更・順序変更・図解消失・小さい文字・非表示・横はみ出しを検出する。
- `quality.py`は同じビルドの表示検査・デザイン検査・最新の検査コードのハッシュを照合。未検査・不合格・古い検査結果では停止する。

意図的な差分：読みやすさのため本文周辺・ボタン・著者説明は16px以上。図解はHTML/CSSの文字付きカードとし、単純縮小しない。ローカル確認用表示・ナビは残す。YouTube文言はリンク機能に合わせ「YouTubeチャンネルを見る」、LINEは「公式LINEで相談する」。未確認の著者資産実績は掲載しない。

試作2記事の図解・まとめは`tools/blog_pipeline/design-content.json`にローカル補足として管理。既存のDrive原稿を変更せず適用できる。今後の原稿は`design.summary`／`design.diagrams`として編集データに含める。今回はDriveへ同期していない。

試作版に対して検査を先に実行し、不一致を検出した結果は`editorial/design-review/pre-alignment-report.json`に保存。最新結果は`dist/blog-preview/design-report.json`、既存LP等の表示検査は`visual-report.json`、最終判定は`quality-report.json`。いずれもローカル作業ファイルで、Git管理外。

この検査は指定されたデザイン・構造を機械判定するもので、文章の事実確認、全ブラウザー互換性、外部サービスの到達性、任意の将来の崩れの完全検出を保証しない。公開承認とは分けて扱う。

## 11. 太字・ハイライトの共通ルール

2026-09-13追加。目的は、50代・60代の読者が流し読みでも確認点と結論を拾えること。強調の数を埋めるためには使わない。以下の数値は本サイトの編集基準であり、一般的な最適値を主張するものではない。

### 使い分け

| 種類 | 用途 | 見た目 | 使用例 |
| --- | --- | --- | --- |
| 太字のみ | 確認項目、混同しやすい言葉、重要な条件・注意点 | 本文と同色、ウェイト700。サイズは変えない | 「預り区分」「予定支出と緊急予備費」 |
| 黄色ハイライト＋太字 | 節の結論、読者が覚えておく判断基準・行動 | 濃い本文文字＋淡い黄色の下部マーカー＋ウェイト700 | 「設定完了と購入完了は別」「同じ費用を二度数えない」 |

太字は単語・短い句を中心に、ハイライトは意味が完結する短い句・文に使う。黄色だけの強調、赤い太字、複数色のマーカー、文字の拡大を重ねた強調は使わない。

### 量と長さ

- 太字のみ：H2の節ごとに0〜2箇所まで。H3があっても親のH2内で合算する。
- ハイライト：記事全体で3〜5箇所を目安、最大5箇所。H2の節ごとに最大1箇所。短い記事など、不要な場合は3箇所未満でよい。
- 1段落・1リスト項目・1表セルの中では、太字とハイライトを合わせて最大1箇所。
- 1箇所は40文字以内。長い文章全体や、複数段落をまとめて強調しない。
- 強調される文字は対象本文の10%以内を目安とし、15%を上限とする。ハイライト＋太字の文字を二重計上しない。
- 対象本文は導入・本文・FAQ回答・まとめの文章、リスト項目、表のデータセル。見出し、図解、表の見出し、ナビ、目次、CTA、著者情報、出典一覧は集計から除外する。
- H2に属さない導入文は1つの節として扱う。FAQとまとめもそれぞれ1つの節として上限を適用する。

### 配置と選び方

1. 導入で最重要の判断基準を提示し、必要ならハイライトを1箇所置く。
2. 本文では確認項目を太字にし、重要な節の結論をハイライトにする。すべての節へ均等に入れない。
3. まとめでは最重要の行動を1箇所だけハイライトにする。同じ文章を各所で繰り返し強調しない。

見出し・図解タイトル・ボタンは部品自体の太字を使い、黄色マーカーは追加しない。リンクはリンクとして識別できる装飾を優先し、ハイライトと重ねない。既に色の付いた注意ボックス内では太字のみを使う。

利益、利回り、還元率、ランキング、口座開設の誘導だけが目立つ強調は避ける。「必ず儲かる」「今すぐ買うべき」などの断定・煽りに強調を使わない。金額や数字を強調するときは、架空例・上限・条件付きなどの前提が切り離されない範囲で選ぶ。

試作記事への適用候補：

- SBI記事：確認項目の「預り区分」「初回買付後」を太字、判断基準の「設定完了を、購入完了と取り違えない」をハイライト。
- 家計メモ記事：「予定支出」「緊急予備費」をそれぞれ適切な段落で太字、「同じ費用を二度差し引かない」をハイライト。架空例の「430万円」だけを強調しない。

### 表示・実装仕様

主基準記事の黄色`#ffe58a`を使用し、文字色は`#333`、下部約42%のマーカーとする。下記は次回実装の仕様例であり、この追記時点ではCSSへ適用していない。

```css
.bp-emphasis { font-weight: 700; }
.bp-highlight {
  color: #333;
  font-weight: 700;
  background: linear-gradient(transparent 58%, #ffe58a 58%);
  -webkit-box-decoration-break: clone;
  box-decoration-break: clone;
}
```

強い重要性は`strong`で表し、ハイライトはその共通クラスとして付ける。色が見えなくても文章だけで意味が通るようにする。スマホで途中改行できるインライン表示を維持し、`white-space: nowrap`や文字列全体の`inline-block`化はしない。

原稿に自由なHTML・CSSを許可せず、構造化した強調指定から安全に生成する。部分文字列の全件置換は行わず、対象の段落と文字範囲を特定する。原稿改稿で一致しなくなった指定は自動で別の場所へ移さず、再確認する。

### 検査への追加仕様と現状

次の実装時に、個数・文字数・強調率・許可色・太さ・禁止箇所・スマホ改行を自動検査へ追加する。強調しすぎ、赤色化、長文強調、リンクとの重なりも故障注入の対象にする。重要な結論か、金融表現を誤解させないかは機械判定だけに任せず編集確認する。
